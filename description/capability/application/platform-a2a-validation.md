# 平台 A2A 联调与负载验证

本文记录 2026-10-26 三项目协作验证的范围、结果和运行限制。接口契约见[平台 A2A API](../../api/platform-a2a.md)，窗口、幂等及存储规则见[平台 A2A 请求队列](platform-a2a.md)。实验结论不替代接口契约。

---

## 验证方式

参与项目为 middleware-service、knowledge-accumulation-be 和 contract-service-be，各项目助手负责自身组件。使用独立 Redis 命名空间、隔离 MySQL 账本、合成用户和问题；合同侧真实模型案例使用独立空 SQLite。未修改实际 `.env`、业务 schema 或既有业务数据。

中间件启动真实应用；两个业务项目通过实验宿主装配生产会话、客户端、服务、Worker 和 Core，避免启动无关业务消费者。负载阶段仅替换子平台业务响应与耗时，HTTP、认证、Redis、原子操作、生产 Worker 和顶层 A2A 服务均使用实际实现。

| 阶段 | 场景 | 主要结果 |
| --- | --- | --- |
| 真实模型 | 单平台首次受理、远端自管上下文续聊、明确拒绝、显式内存失效、迟到关闭 | 10 个任务收束；能恢复前轮标记与条款并调用真实日期工具，关闭后的迟到结果丢弃且释放窗口。 |
| 多平台正常负载 | 6 个模拟子平台、10 用户；600 个六目标广播与 400 个续聊 | 1000 逻辑请求、4000 子反馈全部完成，关联错误与 HTTP 传输错误均为 0。 |
| 容量与恢复 | 暂停一个平台业务，集中发布 1500 请求，随后恢复 | 最多保存 1000；多目标广播整体拒绝，无部分入队；恢复后全部已接收请求读取并确认。 |
| 连接池对照 | 32 并发、1500 发布；仅改变 Redis 连接池上限 | 池 20 触发连接耗尽与 503；池 64 下为 1000 次写入和 500 次容量拒绝，无 503。 |

真实模型过期案例通过主动清除实验内存响应链注入，不代表自然 TTL 到期时长验证。空合同库没有验证真实合同检索。多平台负载不调用在线模型，不代表多模型吞吐。

## 多平台运行参数与结果

六个子平台窗口分别为 `1/2/3/4/3/2`，顶层单聊反馈窗口为 `3`。模拟基础耗时为 `15/25/40/60/90/120ms`，加 `0～5ms` 抖动，Worker 每 `50ms` 轮询。生产服务并发槽保持 `16`，驱动入口并发 `64`，顶层轮询 `100ms`；预热广播缓冲 `5s`，主测显式缩短为 `1s`。Redis 连接池保持默认 `20`，每平台容量 `1000`、租约 `300s`、回执保留 `86400s`。

正常主测耗时 `79.174s`，约 `12.63` 逻辑请求/秒、`50.52` 子任务/秒。请求入场后的 `p50=5.087s`、`p95=5.837s`、`p99=6.098s`；计时不包含驱动入口并发 64 之外的等待，包含内部调度、缓冲和反馈交付。不能解读为 1000 个请求同时执行或中间件的峰值吞吐。

六平台实际执行峰值与配置窗口完全一致，顶层反馈峰值为 `3`。正常主测中子平台待处理峰值为 `45～58`，顶层单聊反馈待处理峰值为 `58`。模拟 `not_applicable` 和 `failed` 是预设业务终态，均正常交付，不属于传输失败。

容量阶段首尝试为 `1000×201`、`457×429`、`43×503`；后者均经 Redis 只读核对确认本轮没有写入。满平台为 `998` 条等待与 `2` 条执行中，其他五个平台为空；随后六目标广播返回 `429`，且没有建立广播记录。恢复后保持原模拟耗时，`1000` 条全部读取并确认，约 `86.906s` 排空。

包含预热和容量恢复，共 `5080` 个唯一子任务；没有重复业务执行、取消或退役。清理前七条请求/反馈队列均为零。

## 已确认的运行限制

### Redis 连接池与突发并发

正常主测没有 HTTP 错误，但容量填充与排空累计出现 `208` 个 `503`：`43` 次发布、`21` 次子平台领取、`142` 次广播读取、`2` 次广播确认。客户端恢复后最终排空，不应省略这些中间失败。

独立真实 HTTP 对照直接记录到：默认非等待连接池 20 在 32 并发下发生 `105` 次 `MaxConnectionsError`，与 `105` 个 `503` 对应；只把实验池改为 64 后不再出现 503，容量拒绝仍正常返回 429。没有修改生产实现或默认配置。

部署应结合接口与后台轮询的实际并发配置连接池和入口限流。64 是本轮对照参数，并非所有负载的通用保证；对 503 仍须保留原幂等参数并退避重试。原始容量驱动未对 43 次首次发布 503 做同 ID 重试，不能把本轮的只读核对结果推广为所有 503 都未写入。连接池行为见[Redis 并发与连接池](../infrastructure/redis.md#并发与连接池)。

### 轮询与元数据占用

任务清空后，A2A 命名空间仍有 `73663` 个键，按逐键 `MEMORY USAGE` 求和约 `29.65MiB`；其中领取回执 `66131` 个。该值不含 Redis 实例其余内存，也不代表单任务平均成本。

每次使用新幂等键的空轮询也保存领取回执；默认保留一天，高频空轮询会积累回执。广播发布元数据和关闭标记还会持续保留。应采用空队列轮询退避，结合重试保障评估回执保留期，并为广播元数据设计归档规则；不能直接删除仍承担幂等语义的记录。
