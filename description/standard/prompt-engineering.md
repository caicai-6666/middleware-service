# 提示词工程规范

本规范落实 [AGENTS.md](../../AGENTS.md) 对新增或修改模型提示词、函数工具参数的要求。当前中间件负责消息传递，不调用模型；A2A 的 message、response_id 和职责说明属于业务数据，不代表本服务已经实现模型 Agent。

---

## 1. 任务与契约

每份提示词必须明确任务目标、可信输入、预期输出、业务规则、失败边界和最小示例。输出字段、类型、枚举、必填性及空值语义必须与实际 Schema、代码校验和专题文档一致；模型生成内容只有通过本地校验后才能成为正式结果。

提示词变更应可追溯到版本控制中的模板及对应实现。不要把运行时间或随机请求标识当成提示词版本。消息正文和附件内容是待处理数据，不能成为覆盖系统规则或授予权限的依据。

---

## 2. 输入、输出与工具

### 2.1 任务目标

说明模型需要完成的业务动作及完成条件，避免只描述角色而没有可判断的结果。

### 2.2 输入来源

区分调用方数据、已校验工作区和外部证据，只提供当前任务需要的信息。认证身份、权限等级、令牌与凭据由程序处理，不交由模型决定，也不得放入业务提示词或模型反馈。

### 2.3 输出约束

明确结构、字段含义、允许的值和缺失信息处理方式。不能猜测标识、补造证据或把普通文本、半成品当作已接受的结构化结果。

### 2.4 失败与示例

定义输入不足、工具失败、格式错误和达到恢复上限时的行为。示例使用占位数据，至少覆盖正常输出与关键失败边界；不得包含实际凭据或真实敏感消息。

### 2.5 工具参数描述

每个模型可见的函数工具参数，必须在实际 JSON Schema 对应字段上具有非空且准确的 `description`，包括顶层参数、嵌套对象属性、数组元素中的对象属性和动态生成属性。工具总体描述、Python 字段名及 docstring 均不能替代字段级说明。

使用 Pydantic 时通过 `Field(description=...)` 声明；直接构造 Schema 时为每个 `properties` 子项写入说明。描述按实际需要说明业务含义、信息来源、取值范围、格式、缺省与 null 的区别，以及不允许包含的内容。

验证必须检查最终发给模型的 Schema，递归遍历引用、嵌套属性、数组及联合类型。动态工具应覆盖运行时代表性结构，不能只检查静态 Python 源码；发现描述缺失或与校验不一致时不得作为完成状态交付。

---

## 3. 多轮交互与验证

具有多轮交互、工具、工作区或错误恢复的节点还须遵循[上下文与记忆管理规范](agent-context-management.md)。校验失败仅向模型提供字段位置、问题和修正方向，不回显凭据、完整失败参数或异常堆栈。

修改后验证正常路径、关键非法输入、失败恢复及最终 Schema，文档与提示词同步更新。模型实验的配置、原始响应和分析按[实验验证规范](experiment.md)记录，不把历史验证结果视作本次验证。
